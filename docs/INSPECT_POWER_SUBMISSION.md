# Read-only inspection of Power entry 21

The script checks the submission made on 18 September 2026 against current
MongoDB records and the upload/datastore mounts. It does not depend on the new
Power monitoring endpoint or any undeployed API code.

Copy these **two files only**, keeping them together, to `/tmp` on the API host:

- `scripts/inspect-power-submission.cjs`
- `scripts/power-entry-21-2026-09-18.json`

Run as the usual API service account, using its normal Node environment:

```sh
cd /storage/www/komondor-api
node /tmp/inspect-power-submission.cjs --json > /tmp/power-entry-21-report.json
```

Share `power-entry-21-report.json` for diagnosis. Omit `--json` to print a readable
report. Exit code **0** means the checks agree; **1** means the report contains
missing, unfinished or inconsistent items; **2** means inspection could not
finish (the reason is printed to stderr).

It resolves the already-installed `mongoose` and `dotenv` dependencies from the
current API directory. It reads that directory's `.env`; existing shell
environment variables take precedence. A separate shell does not automatically
inherit PM2-only settings. Use `--env /path/to/api.env` if needed. Configuration
requires `MONGODB_URI` (or an explicit `MONGODB_PORT`, using the API's legacy
`localhost:<port>/komondor` convention), `HPC_TRANSFER_DIRECTORY` and
`DATASTORE_ROOT`. There is no guessed database connection when both Mongo
settings are absent. Mount paths can be overridden with `--hpc-root` and
`--datastore-root`. No credentials or MongoDB URI are included in the report.

## What it checks

The companion manifest contains the **24 exact run IDs** from the API log,
matched by run name to the **48 read files and expected MD5s** in entry 21 from
the provided SQLite production copy. It includes the project, submitter,
submission timestamp and a fingerprint of that entry's metadata CSV. Sample
conditions and the rest of the CSV are not needed. The production Power SQLite
database is not opened by this script, and its historical `error` status is not
changed.

- Expected project/sample/run relationships and owner; missing IDs and other
  runs with matching names under the same project/sample.
- Ingest job state, run processing state and recorded checksum outcome.
- Read-to-File references, submitted MD5 versus recorded original/destination
  MD5, and legacy mismatches even when the old run status says `complete`.
- Accessibility and sizes of each upload source and final datastore file;
  empty, missing, unreadable and unexpected paths are flagged.
- Path comparisons account for the API model's slash-prefixed `Run.path`
  (for example `/group/project/sample/run`) and datastore-relative `File.path`
  (`group/project/sample/run/raw/reads.fq.gz`). Report version 2 includes both
  stored paths and the expected path for each read. Version 1 incorrectly
  flagged the leading-slash difference; that finding alone does not indicate
  misplaced files. Absolute file paths and traversal remain rejected.
- The filesystem/mount covering each configured root on Linux, from
  `/proc/self/mountinfo`. This helps identify a missing NFS mount when a plain
  local directory exists at the expected location. The report describes the
  observed mount; it does not assume every installation uses NFS.

A staging source missing after a successful move is normal; a retained source
is also supported. A source's presence alone does not establish successful
ingest. If both files exist, their sizes are compared.

## Optional independent checksum check

The default mode uses **stored MD5 results and file metadata**. It does not
independently prove that current bytes still match. For that, run:

```sh
cd /storage/www/komondor-api
nice -n 10 node /tmp/inspect-power-submission.cjs --hash --json > /tmp/power-entry-21-rehashed.json
```

This reads each destination file in full, sequentially. It may take a while and
adds disk/NFS read traffic; it never changes stored checksums. Changes observed
while a file is being hashed are flagged. The report is a live observation, not
an atomic snapshot of the worker and filesystem; rerun if jobs are still active.

The script uses the Mongo driver's read operations directly. It imports no API
models, starts no workers, creates no indexes, moves/deletes no files, writes no
application records and sends no email. Only the shell redirect writes a report.
File reads may update filesystem access times according to mount settings.

## Automated verification

`__tests__/scripts/inspect-power-submission.test.js` covers manifest scope,
argument validation, path containment, symlinks, missing files and hashing.
`__tests__/integration/power-submission-cli.test.js` runs the actual CLI against
scratch MongoDB and files, with group/project/sample/run paths generated by the
real API models. It checks slash-prefix compatibility and genuine path
mismatches as well as successful legacy records, corruption,
missing bytes/IDs, mismatches, duplicates, active jobs, retained sources and
credential redaction. Before/after snapshots verify documents, indexes and file
contents are unchanged. The integration suite requires an explicitly configured
scratch `MONGODB_URI`, as do the repository's other integration tests.
